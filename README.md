**A browser agent with a dynamic, indexed action space.**

Give it one goal. [TypeSafe's Jev](https://docs.typesafe.ai/introduction) picks an operation and an element. A small LLM writes text only when the operation is `TYPE_TEXT`.

**Zürich → London on Google Flights in 7.1 seconds.** One natural-language goal, actual text generation, and loading waits included.

## The action space

Every observation produces a new element table:

```text
[1] button    Change ticket type · Round trip
[2] combobox  Where from?        · San Francisco
[3] combobox  Where to?          · empty
[4] textbox   Departure          · empty
...
```

The operations are `CLICK`, `HOVER`, `TYPE_TEXT`, `SELECT`, `PRESS_KEY`, `GOTO`, `BACK`, `RELOAD`, `SCROLL_UP`, `SCROLL_DOWN`, `WAIT`, `DONE`, and `BLOCKED`. Only supported operations and targets are offered. `HOVER` moves the pointer without pressing, for menus and tooltips that open on hover; it is offered only for elements that hint at a hover effect (`revealed_by`, `aria-haspopup`, `aria-expanded`, a non-empty `title`, or `aria-describedby`) and is left out entirely when none does. Controls that are hidden only by `opacity` until their row is hovered or focused are listed with `revealed_by: "hover"`; `CLICK` moves the pointer onto them, waits up to `reveal_timeout_ms` (default 500) for them to appear, and never presses one that stays transparent. Every click is preceded by a pointer move, and after the move the target is located, hit-tested and compared with its observed guard again (identity, role, name, value and state, `href`; not the surrounding text, which hover legitimately changes), so a page that relabels the control on hover, or covers or moves it, is refused instead of pressed. A refused press is recorded in `state["refused"]` (not in the history), shown to the model as a refused recent action, hidden from the next choice while the page is unchanged, and counts toward `stuck_after`. A control is a hover reveal only when one transparent layer (the control or a close ancestor) sits directly under a visible parent that is not `body`, and neither that layer nor any element between it and the control is `position: fixed`, a dialog (`dialog`, `role="dialog"` or `"alertdialog"`, `aria-modal="true"`, `[popover]`), and the layer itself covers at most a quarter of the viewport. A closed `opacity: 0` dialog, or a large opacity-0 mobile nav panel, is therefore not listed even inside app wrappers, while a toolbar in a tall message is. The remaining limit: a small, non-fixed, non-dialog transparent popover is still listed; a refused press on it is bounded by `stuck_after`.

```text
                      one TypeSafe request
                     ┌───────────────────────────┐
page → element table → operation                 │
                     │ click_target              │
                     │ type_text_target          │
                     │ select_target, if present │
                     └─────────────┬─────────────┘
                         use the matching target
                                   │
                    CLICK [7] ─────┤──→ browser
                TYPE_TEXT [3] ─────┘
                          ↓
                   small LLM → text → browser
```

Target questions are speculative. If the operation is `CLICK`, only `click_target` can execute. Two decisions, **one network round trip**. Each target head contains only compatible elements. Native dropdown choices carry an observed element/option index.

There are no site-specific action scripts or prepared field strings in the policy. The Flights example supplies a goal and independently verifies the outcome. The screenshot renderer adds labels afterward; it does not drive the browser.

## Use the library

```python
from jev_ultrafast import Agent

with Agent(
    "https://www.google.com/travel/flights?hl=en",
    "Find one-way flights from Zurich to London on September 20, 2026, "
    "for one adult in economy. Stop when matching flight options are visible.",
) as agent:
    for state in agent.run():
        print(state["elapsed_ms"], state["status"])
```

Run with `uv run --env-file .env python your_script.py`. The same policy can run a different task:

```bash
uv run --env-file .env python examples/run.py \
  --url https://en.wikipedia.org/wiki/Main_Page \
  --goal 'Find and open the Wikipedia article about Gödel’s incompleteness theorems.'
```

`uv run --env-file .env python examples/flights.py --keep-open` performs the flight search, checks the actual route/date/results, and saves its trace. It does not select or book a flight.

### Driving a page you own

A test runner that already has the page open (Playwright over CDP, with its own evidence and steps) can hand one step to the agent on that same tab. Pass the CDP target id instead of a URL:

```python
from jev_ultrafast import Agent

# page = a Playwright page connected over CDP
target_id = page.context.new_cdp_session(page).send("Target.getTargetInfo")["targetInfo"]["targetId"]

with Agent(goals="Open the billing settings", target_id=target_id) as agent:
    for state in agent.run():
        pass
```

With `target_id` the agent attaches a session to that tab and does not create a target, navigate, or change the viewport (pass `viewport=` to set one). Pass `url` as well to navigate the attached tab first. Snapshots, waits, evidence capture and replay work as usual. `close()` only detaches: the tab stays open. `new_window` and focus emulation apply only to tabs the agent creates. An unknown `target_id` raises `ValueError`; with neither `url` nor `target_id`, so does construction.

### Keys and navigation

`PRESS_KEY` sends one key to the element that has focus (marked `focused` in the element table), or to the page when nothing does. The model chooses among `Enter`, `Escape`, `Tab`, `Shift+Tab`, the arrow keys, `Space`, `Backspace`, `PageUp`, `PageDown`, `Home`, `End`, and any shortcut chords you declare. It never writes a key or a URL. `BACK` is offered only while the tab has a previous history entry (read from the browser's navigation history, not `history.length`, which also counts forward entries), `RELOAD` always, and `GOTO` only for pages you declare.

```python
with Agent(
    url,
    "Open the command palette and search for billing",
    keys=("Control+K", "Meta+K"),
    urls={"Settings": "https://app.example.com/settings"},
    navigation_timeout_ms=15000,
    cdp_timeout_ms=15000,
) as agent:
    for state in agent.run():
        pass
```

Declared chords are `(Control|Alt|Shift|Meta)+...+Key`, with at least one modifier and a key from the fixed set, a single letter or digit, or `F1` to `F12`; anything else raises `ValueError` at construction. URLs must be absolute `http(s)` URLs without credentials. After `BACK`, `RELOAD` or `GOTO` the agent waits for a new document (at most `navigation_timeout_ms`) and then observes even if the page is still loading. A `BACK` that finds no previous page sends nothing and is recorded like a refused press (`state["refused"]`, hidden from the next choice, counted by `stuck_after`). All of these are browser mutations: they are logged before the observation, never retried, count toward `max_steps` and `stuck_after`, and pass through `before_action` with `kind` `key`, `back`, `reload` or `goto`. A key action carries `key` and `focused` (`role`, `label`, `href`, `tag` and `type` of the focused element, or `None`), so a policy can refuse, for example, Enter on a focused Delete button; `goto` carries `url`. A policy that refuses `kind == "click"` on a control must also handle `kind == "key"` on the focused element, because Enter or Space on a focused Delete button activates it just like a click. The value of a focused password, file or hidden input is never read: its identity guard holds only its type and accessible name, and Enter on it still works. Keyboard focus is part of what the model sees, but moving focus alone is not progress: `stuck_after` compares the page without focus, so a model that keeps pressing `Tab` over the same inputs ends `blocked`. A key press is refused as stale unless the focused element (its node and guard) is still the one observed. The key head costs about 2.9 KB flat per request (the head's rule text plus 14 key choices); it does not shrink noticeably with fewer keys. Limits: keys go through the browser's input path, so a page that ignores synthetic key events or traps focus in a frame or shadow root is out of reach, and a key cannot type text (use `TYPE_TEXT`). Builds on the idea in [browser-use/jev-ultrafast#211](https://github.com/browser-use/jev-ultrafast/pull/211).

### Per-call timeouts

Every CDP call the library makes waits at most `cdp_timeout_ms` (default 15000, on `Agent` and `Browser`) for the browser; browser-harness alone waits 5 s, which a heavy single-page app can exceed on `Page.navigate`, `Runtime.evaluate` or an input event. `Page.navigate`, reload, back and the document wait keep `navigation_timeout_ms`. A **read** that times out (observing, the freshness check, a snapshot, a locator or resolve, a screenshot, a wait slice) is treated like a stale page: the agent observes again (a wait slice is just an unmet slice), and a replay does the same when resolving a recorded element times out instead of calling it a divergence. A locator read for the trace is tried once more before the step is left without one. Two read timeouts in a row in one `observe()` end the run `failed` with `stop_reason: "read_timeout"` instead of raising, also when the look-again of a tick times out. A **mutation** that times out (an input event, a key, a navigation, creating the tab) may or may not have been applied, so it is never retried. `Browser` raises `MutationTimeout` naming the call (`Input.dispatchMouseEvent timed out after 15s waiting for the daemon; it may have been applied, so it was not retried`); the `Agent` records the action as unconfirmed (history `executed: "unknown"`, a `mutation_timeout` trace event with the CDP method) and ends the run `failed` with `stop_reason: "mutation_timeout: <method>"`, so a later tick never sends it again. A select whose script does not answer counts as one. Mouse moves and wheel turns are mutations too, although harmless to repeat: the whole `Input.dispatchMouseEvent` family is never retried. A tab whose creation timed out may stay open (the library never got its id). A failed `close()` does not hide the exception that is leaving a `with Agent(...)` block.

### Waits

`WAIT` no longer sleeps 0.1 s. It waits in code, without a model call, until the page is settled: the document is loaded (also after a script navigates meanwhile), no `fetch` or `XMLHttpRequest` is in flight or finished within `wait_quiet_ms` (default 500), no short timer that was pending when the wait began is still pending, and the DOM has not mutated for `wait_quiet_ms`; it gives up after `wait_timeout_ms` (default 30000). One `WAIT` therefore covers a whole streamed answer or a results page that loads after a request. A `WAIT` goes through `before_action` like every other action, and skips only the freshness check (a page that is still streaming is never fresh; a wait changes nothing, and every later press re-checks). It is recorded in the history with `waited_ms` and `met`. For `stuck_after` a `WAIT` that was met is progress, a `WAIT` that timed out while the content changed (a stream longer than the timeout) is progress, and a `WAIT` that timed out on an unchanged page is an unchanged step, so a model that keeps waiting on a page that never settles ends the run as `blocked` after `stuck_after` of them instead of burning `max_steps` times `wait_timeout_ms`.

After every other action, the existing settle (50 ms, 200 ms for comboboxes) stays. If at its end a counted request is in flight or started since the action began, or a short timer was armed since then (the baseline is read right before the input is sent, one small browser call), the same wait runs, bounded by `action_settle_timeout_ms` (default 5000, `0` turns it off), so "click, fetch, render" and "click, timer, navigate" are already done when the next observation is read. When nothing is pending it adds no browser call: the settle script returns the tracker counters it already reads. Timers and requests the page started before the action (a polling chain, a long poll) do not trigger it, however long the model took to choose: a polling page that arms a timer every 400 ms costs a click nothing. Requests with a non-`http(s)` URL (`data:`, `blob:`) are never counted, and relative URLs are resolved against the document base URL (`<base href>`), as the browser does.

Callers (test runners, assertions) can wait directly. Each call is bounded by `timeout_ms` (default 30000), costs no model call, never raises on timeout, and returns a `WaitResult(met, waited_ms, reason)`; the last 100 are kept in `state["waits"]`:

```python
agent.wait_for("settled", quiet_ms=500)
agent.wait_for("dom_quiet", quiet_ms=300, ignore_attributes=("style",))
agent.wait_for("network_idle", idle_ms=300, ignore_urls=["/poll", re.compile(r"/long/\d+$")])
agent.wait_for("element", role="button", name="Copy")                       # present (visible anywhere in the document)
agent.wait_for("element", role="button", name="Stop generating", present=False)
agent.wait_for("element", role="checkbox", name=re.compile("^Email"), state={"checked": True})
agent.wait_for("text", "Report ready")                                       # or a compiled regex; present=False waits for it to go
agent.wait_for("text_stable", quiet_ms=500, role="textbox", name="Answer")   # the text of that element (or the whole page without role/name) is unchanged
```

`role` is one of the roles the snapshot understands (`button`, `link`, `checkbox`, `textbox`, ...); `name` is the accessible name, exact or a compiled regex; `state` is a name, a list of names, or `{name: bool}` from `checked`, `expanded`, `selected`, `pressed`, `disabled`. The same role and name code serves the snapshot and the waits (`jev_ultrafast/a11y.js`). A regex is evaluated by the page's JavaScript `RegExp`: only the `re.IGNORECASE`, `re.DOTALL` and `re.MULTILINE` flags are carried over, and Python-only syntax (`(?P<name>...)`, `\A`, `\Z`, inline flags such as `(?i)`, possessive quantifiers, atomic groups, conditionals, comments) raises `ValueError` up front. A bug in a wait inside the page raises `ValueError` with the page's message instead of spinning until the timeout. `state` reads ARIA attributes (and the native `checked`/`disabled` state), so a native `<details>`/`<summary>` is never `expanded`; give it `aria-expanded`. Python `\d`, `\w`, `\s`, `\b` match Unicode and `$` also matches before a trailing newline, while the page's JavaScript `RegExp` is ASCII-only there and strict: write the pattern for JavaScript. `text_stable` on an element asks for some text by default (`require_text=True`), so an element that has not started to fill is not "stable"; the whole-page form does not (`require_text=False`).

Knobs on `Agent` (and `Browser`):

| Argument | Default | Meaning |
| --- | --- | --- |
| `ignore_urls` | `()` | Substrings or compiled regexes, matched against the absolute URL, for long-lived `fetch`/`XMLHttpRequest` requests (long polls, beacons) that no wait and no post-action trigger counts. Callers can add more per call. |
| `wait_timer_ms` | `2000` | A one-shot `setTimeout` of at most this long that is pending when a wait begins holds it until it fires. Timers armed later (a polling chain re-arming itself) never do. `0` turns timer counting off. |
| `body_cap_ms` | `30000` | The longest a `fetch` keeps counting as in flight after its response headers arrived. |
| `wait_ignore_attributes` | `()` | Attribute names (for example `("style",)`) whose changes are not DOM activity, for pages that rewrite them every frame. |
| `wait_interactive_grace_ms` | `2000` | How long a document may stay `interactive` (a hung image, script or beacon keeps it from `complete`) with nothing counted in flight before it counts as loaded. |
| `new_window` | `None` | See "Keep the owned tab rendering". |
| `viewport` | `(1120, 780)` | `(width, height)` of the owned tab in CSS pixels (positive integers, at most 7680x4320; also a `Browser` argument). Responsive pages change layout with it: a navigation that collapses, a sidebar that hides or a side panel that opens below some width. The scroll wheel turns over the middle of the viewport, and one scroll step is `round(height * 560 / 780)` pixels (560 at the default, at least 1), so a step never skips content at a short viewport. Recorded in `run_start.viewport` and the `config`. |

How activity is counted. browser-harness delivers CDP events only through one shared, destructive buffer of 500 events for all sessions (a drain by anyone else empties it), so Jev does not use `Network.*` or `Page.*` events. Instead a small tracker (`waits.js`) is installed with `Page.addScriptToEvaluateOnNewDocument` before the page's own scripts run. It never changes what the page sees: `fetch`, `XMLHttpRequest.open/send`, `setTimeout`, `clearTimeout` and `clearInterval` are `Proxy` objects that forward every call, argument, `this` and return value untouched (`fetch.name` is still `fetch`, `fetch(...)` returns a promise derived from the browser's own, which settles one microtask later with the same response or the same error and stays unhandled exactly when the page leaves it unhandled, so `unhandledrejection` still fires once; the response itself is never cloned, teed or wrapped, so cancellation reaches the server and a slow reader still applies backpressure).

- A `fetch` counts from the call until its promise rejects, the page aborts it through its `AbortSignal`, or the browser reports its `PerformanceObserver` resource entry (paired by absolute URL, oldest first). Measured on Chrome: that entry arrives when the body is read to the end or cancelled, and not at all for a body nobody reads. So a response whose body has not been requested 500 ms after its headers (`response.bodyUsed` is still false) stops counting, and `body_cap_ms` after the headers is the hard cap for a body that is read slowly or never finished. A body the page starts reading late can therefore be missed by `network_idle`; `dom_quiet` and `text_stable` cover what it renders.
- An asynchronous `XMLHttpRequest` counts until `loadend`, until the page `open()`s the same object again (which abandons the request without any event), or `body_cap_ms` after `send`. Synchronous XHR, WebSockets and `EventSource` are never counted.
- Timers: see `wait_timer_ms`. `setInterval` is not counted. The threshold is a boundary, not a judgement: a toast that auto-hides in 1.5 s holds a wait for up to 1.5 s, and a page that redirects after 3 s is not waited for; change `wait_timer_ms` for such pages.
- DOM mutations come from one `MutationObserver` (child list, character data and attributes by name).

Limits: only the main frame's own requests are seen (not iframes, workers or service workers, nor images, scripts and styles, which `document.readyState` covers); a page that polls with `fetch` needs that URL in `ignore_urls`; a page that animates through `requestAnimationFrame` and rewrites DOM attributes every frame never gets a quiet DOM unless those attributes are listed in `wait_ignore_attributes` (measured on a `style` animation in CI: 700 ms of `dom_quiet` timeout versus met at once with `style` ignored; the default stays empty because a script that shows or hides content through `style` alone is a real change); and `element`, `text` and `text_stable` scan the document, so they poll at four times what one check costs (50 to 250 ms) rather than every 15 ms.

### Budgets and policy

Bound a run and veto actions without touching the agent's internals:

```python
from jev_ultrafast import ActionDenied, Agent

def no_deletes(action, page, text):
    if "delete" in action["label"].lower():
        raise ActionDenied("Delete controls are off limits")

with Agent(url, goal, max_steps=20, max_model_calls=40, before_action=no_deletes) as agent:
    for state in agent.run():
        pass
print(state["status"], state["stop_reason"], state["denied"])
```

`max_steps` bounds executed actions. `max_model_calls` bounds TypeSafe decisions plus text-helper calls (default `2 * max_steps`) and is checked before each call. `max_steps` is checked when an action would execute, so the decision that discovers the cap still counts as a model call. Reaching either ends the run with status `budget` and `state["stop_reason"]` (`max_steps` or `max_model_calls`) instead of an exception. `settle_ms` (default 50) and `autocomplete_settle_ms` (default 200, both may be 0) cap the wait after an action, and `stuck_after` (default 3) unchanged steps end the run as `blocked` (see Waits for which waits count). `before_action(action, page, text)` runs before each execution attempt, with the final typed text and copies of `action` and `page`. It can run more than once for one intended action if the page goes stale first, so keep it free of side effects or make it idempotent. A veto always prevents execution: raising `ActionDenied` executes nothing, records no history entry and ends the run as `denied`. Any other exception from the hook propagates.

### Steps and checks

A goal can be a list of steps, and a step can carry checks that the code evaluates, so DONE is not just the model's word:

```python
from jev_ultrafast import Agent, Step, Value, expect

steps = [
    Step("Search for the term", expect=[expect.text("Results for cats")]),
    Step("Open the first result", expect=[expect.url("/cats"), expect.text("Cat facts")]),
    Step(
        "Mark it as a favourite",
        expect=[expect.element(role="button", name="Favourite", state={"pressed": True})],
    ),
]
with Agent(url, steps, values={"term": "cats"}) as agent:
    for state in agent.run():
        pass
print(state["status"], state["verified"], [s["status"] for s in state["steps"]])
```

- **Steps.** `Agent(url, goals)` takes a string, or a list of strings and `Step(goal, expect=(), values=None, params=None)`; each item is one step. The model sees only the current step's goal, the goals already completed and the descriptions of the current step's checks, never the later steps. `state["steps"]` records, per step, `goal`, `status` (`pending`, `active`, `done`, `failed` or `blocked`), `checks` (description, `met`, `reason`, `waited_ms`), `started_ms`, `ended_ms`, `model_calls`, `actions` and `rejections`; `state["plan_index"]` is the current step. A plain string is one step with no checks and behaves as before; a list of strings is now one step per string (it used to be joined into one goal; to get the old behaviour pass `"\n".join(goals)` as one string - the measurements in `docs/` were taken that way, and `examples/flights.py` and `examples/run.py --goal` now run one step per goal).
- **Goal parameters.** A goal often has to name something that only exists in this run: a record an earlier step created, its generated title, an order number. Writing it into the goal text makes the goal differ per run, so a replay refuses the trace (`replay_mismatch: goals differ`). Put a `{name}` placeholder in the goal and in the checks, and fill it with `params`:

  ```python
  title = f"Order {order_id}"  # created by an earlier step, different on every run
  steps = [
      Step("Create an order", expect=[expect.text("Order created")]),
      Step("Open the row titled {title}", expect=[expect.text("Opened {title}")], params={"title": title}),
  ]
  ```

  The rules:
  - The model, the evidence and the `before_action` hook see the rendered goal ("Open the row titled Order 17"), so the model can find the row by reading its name.
  - Placeholders are `str.format` style plain names; write `{{` and `}}` for literal braces. They are filled in the goal, in the string inputs of a check (`expect.text`/`no_text` `contains`, `expect.element` `name`, `expect.url` match; the page is searched for the rendered value) and in the description of an `expect.check`. A compiled regex is never rendered. In a check string, braces that are not a placeholder are doubled too (`expect.text('{{"a": 1}}')`) once the step has params. Without `params`, or with an empty dict, the goal and the checks are literal.
  - Construction raises `ValueError` for a placeholder with no param, a param nothing uses, a param value that is empty, only whitespace, longer than 2000 characters or holds a newline or control character, a param named like a declared value, or a param value that contains a declared secret.
  - **A step with params must have a check that uses one** (a placeholder in a check string or in an `expect.check` description), and `Agent(..., replay=...)` raises when it has none. Why: a replay resolves the recorded element by its locator (role, name, scope, test id), and that no longer says anything about the param value, so a test id that moved to another order would still be clicked. The check is what proves the right object was acted on: on replay the step counts as verified only when it holds. A callable check names its param in the description, and it is up to the callable to use it.
  - A recorded locator scope (a list item or row named by its first text) whose name equals a param value at record time is stored as the param's NAME (`{title}`), never the value, and a replay looks for the scope named by this run's value. A row whose title changes on every load therefore still resolves inside the row you named, without a model call; if no row carries that title the step diverges (heals), even when the recorded test id or stable `id` still exists elsewhere. A varying name that is not a param still makes that step heal. Binding is by equality of text, not intent: an unrelated row whose name equals a param value is bound too, and a replay with another value looks for a row of that other name. The scope stays literal (and heals when the name changes) when two params share the value, when the value is longer than the 80-character scope clip, or when it holds a character outside the Basic Multilingual Plane (the page clips by UTF-16 unit, Python by code point, and they agree only there).
  - **A param is read by the model as part of its instruction.** Params are data shown to the model, not secrets (use `values=` with `secret=True` for those), and never pass text that came from the page or from untrusted input.
  - A trace (schema 2, additive) records each step's goal template, check templates, param names and the rendered params (scrubbed like the rest). A replay compares the templates and the param names and never the param values (whitespace in the templates is ignored), so pass this run's params when you replay; a trace from an older run without templates compares the rendered goals as before.
- **Checks** are `expect.text(contains)` / `expect.no_text(contains)` (a string or a JavaScript-compatible compiled regex), `expect.element(role, name, state)` / `expect.no_element(...)` (the `element` wait), `expect.url(pattern)` (a substring, or a compiled regex that is searched), and `expect.check(fn, description, auto=False)` for a callable `fn(page) -> bool | (bool, reason)`, where `page` is a read-only facade (`evaluate`, `url`, `probe`, `element`, `text`; no `act`, `press`, `goto` or `close`). Each has a description that the model sees and the state records. Each takes `timeout_ms=` to override `expect_timeout_ms` (default 5000), the longest it waits for the page to catch up, so "the upvote is pressed" can wait the few hundred milliseconds the UI needs. A check never raises on timeout, and a callable that raises is recorded as unmet with its (redacted) message. Checks are page-global: a step whose action navigates away is checked against the page that is open afterwards, so pair it with `expect.url`. A negative check (`no_text`, `no_element`) holds on a blank page and on a dialog that never opened, and a step whose checks already hold when it starts completes after its first action; give such a step a positive check for the state you want. **A check callable must be read-only, idempotent and fast.** It is never interrupted, it is polled every 50 ms until it holds or its timeout passes (a DONE can run it dozens of times), `evaluate` still runs whatever JavaScript you give it, and the worst case of one DONE is `len(checks) * timeout` plus the settle wait (`expect_timeout_ms`) plus one more read, up to `max_rejections` times per step. A callable is not read after every action unless you pass `auto=True`, and a step with a callable that did not opt in never completes without a DONE decision. A coroutine function is refused (`async def`).
- **DONE is verified.** On a step with checks, DONE is accepted only when all hold, and again once the page has settled (`Browser.settled`, at most `expect_timeout_ms`): every check is read a second time, so a press that an optimistic UI applies and then takes back does not count. If either read fails, DONE is rejected: the step does not change, the history gets an entry with `kind: "done_rejected"` and the failed descriptions, and the model sees it as a recent action (`DONE rejected: element button "Favourite" pressed=true not met`). A rejection costs a model call, is not an action (`max_steps`, `stuck_after`), and `max_rejections` (default 3) rejections on one step end the run as `failed` with `stop_reason: "expectations"`. A step without checks accepts DONE as before and is recorded with `verified: false`.
- **Auto-complete.** After every executed action, the current step's checks are read once without waiting; if they all hold, the page is settled and every check is read again, and only then does the step complete with no DONE decision, so the run does not depend on the model noticing it is finished. If the second read fails, that counts as a rejected DONE (recorded, shown to the model, toward `max_rejections`). An unmet built-in check costs one browser round trip (about a millisecond, measured with `expect.element`); a callable costs whatever it does, which is why it only takes part with `auto=True`. `auto_complete=False` turns it off.
- **Verified runs.** `state["verified"]` is `True` only when every step had checks and they held twice, across a settle, at completion. `require_expectations=True` makes a step without checks a `ValueError` at construction, for test runners that never want an unverified pass. `failed` is a terminal status next to `done`, `blocked`, `denied` and `budget`.
- **Values.** `values={name: str | Value(text, secret=False)}` on the `Agent` (every step) or a `Step` (that step, overriding) are strings the caller already knows: a search term, a code. `TYPE_TEXT` then has a value choice among the declared names, plus `GENERATE` when a text helper is configured. Choosing a name types that exact string with no text-model call; the model chooses by name and sees the text only where the page or the history shows it (the typed text appears in the field and in the recent actions), unless the value is secret. With values and no text helper, `TYPE_TEXT` also offers `NONE` ("no declared value fits"): choosing it types nothing, records a skipped field (hidden from the next choice while the page is unchanged; unlike a refused press it does not count toward `stuck_after`, because each skipped field is hidden and `max_model_calls` bounds the loop), and `NONE` and `GENERATE` are reserved names. The history records `text_source` (`value:<name>` or `generated`) and `value_name`. A `Value(..., secret=True)` (at least 4 characters; a short one replaces every occurrence, so "1234" also changes "$1234.00" in what the model reads) is shown as `<secret:name>` in the history, in `state`, in the page the model reads (the copy of the observation that the agent keeps replaces the text wherever the page echoes it, for example in the field's own value or in a confirmation message), and as the `text` argument of `before_action`, which also gets the name as `action["value_name"]`; only the browser receives the real text. The observation that the agent keeps is scrubbed before anything else sees it (also the first one), the exposed fingerprint is computed from the scrubbed page, check reasons, wait results and text-call records are scrubbed, generated text that contains a `<secret:` marker is refused, and a goal or check description that contains a declared secret is a `ValueError` at construction. The scrub covers the text as typed and its percent-encoded, plus-encoded, JSON-escaped and HTML-escaped forms. Limits: it is exact and case-sensitive, so a page that upper-cases, re-spaces or shortens the secret (the page text is cut at 6000 characters, so a secret straddling the cut leaks its prefix) is not caught; password inputs are not offered as targets at all (the snapshot skips them), so a secret goes to an ordinary field; screenshots (`screenshots=True`, or the files an `evidence_dir` run saves) are images of the page and are not redacted; a check callable and `expect.text` see the real page.

### Run evidence

```python
agent = Agent(url, goals, evidence_dir="runs/signup-1", screenshots="actions")
```

`evidence_dir` (a new or empty directory; off by default) makes the run write what a test runner needs to explain a failure:

- `trace.jsonl`: one JSON object per event, each with `t_ms` and `type`. `run_start` (library version, browser, viewport, `trace_schema`, the goals with their check descriptions, declared value **names** with their secret flag, the non-secret `Agent` configuration, and whether console and network were captured), `observe` (url, title, fingerprint, element count, focus, screenshot), `decision` (operation, target, top five probabilities, confidence, latency, usage, model), `action` (kind, label, choice, locator, text source, typed text or `<secret:name>`, key, url, value name, result; schema 2 adds `step`, `source`, `name`, `option` for a select, `delta` for a scroll, `focus` for a key, the element that had focus, `focus_locator` for a key, the locator of that element, and `page_url`, the page the action ran on, redacted), `wait`, `check`, `step`, `refused`, `denied`, `done_rejected`, `heal` (schema 2) and `run_end` (status, stop reason, verified, totals: steps, actions, Jev calls, text calls, tokens by kind, wall time). `trace_schema` is 2; `jev_ultrafast.trace.load_trace(path)` reads and validates schemas 1 and 2 and raises `ValueError` for any other, and for a `heal` event inside a schema 1 trace (a schema 1 writer never wrote one). A schema 1 trace can still be replayed; its keys, scrolls, backs, reloads and waits always heal (it did not record the focus, the distance or the page) and a select without a recorded option heals.
- `screenshots/NNNN.jpg`, each referenced from its trace event. `screenshots="actions"` (default) saves the first page, the page after every executed action and the last page; `"all"` also saves every other observation; `"failure"` saves only the last page, and only when the run does not end `done`; `"none"` saves none. Screenshots are images of the page and are **not redacted**; every other file is.
- `console.jsonl` (console calls, uncaught exceptions with the top stack frame, browser log entries), `network.jsonl` (one line per request: method, url, resource type, status, mime type, start, time to first byte, duration, encoded size, failure text, served from cache; no bodies and no headers) and `network.har` (HAR 1.2 from the same data). They come from a websocket of their own, attached to the agent's tab before its first navigation, so they need `BU_CDP_URL` or `BU_CDP_WS`; without either, `run_start.capture` says why they are unavailable and the run continues. Each stream keeps the first 3000 entries, a ring of the last 1000, and a ring of the last 500 errors (console errors and uncaught exceptions; failed or 4xx/5xx requests), so a page that logs in a loop never pushes out the failure that ended the run; `run_end.dropped` counts what was left out (`console` and `network`: the entries between the head and the tail that are not errors, as `run_end.dropped_part` says; `errors`: events that could not be read). A console line, stack or URL is cut at 2 KB (8 KB for a stack) and the record lists the cut fields in `truncated`; websocket frames above 8 MB close the connection; `Network.enable` is asked to buffer almost no response bodies (`maxTotalBufferSize`, `maxResourceBufferSize`, both in the DevTools protocol; a Chrome that rejects them gets a plain `Network.enable`). If the connection ends before the run does (the tab crashed, the browser closed the socket), `run_end.capture_lost` says when and why and the report says so on its first lines: an empty console list then does **not** mean a clean page. The connection and its thread are closed by `Agent.close()`, which is also what writes `report.html`, the final `console.jsonl`/`network.jsonl`/`network.har` and the final `run_end.dropped`; a run that is never closed has only `trace.jsonl` (flushed per event).
- `report.html`: one static page (no scripts, no external assets, a `Content-Security-Policy` of `default-src 'none'`) with the steps, every action with its screenshot, checks, refusals, console errors and failed requests. Screenshots beyond 12 MB in all are linked from the run directory instead of embedded, and the page says so.

Declared secrets pass through the same scrub as the history. **URLs** are redacted by default (`evidence_urls="redacted"`): every URL the run writes (network.jsonl, network.har with its `queryString`, `observe.url`, console and stack URLs and any URL inside a console line, the focus and locator `href`, the report) keeps origin and path, replaces each query **value** and the fragment with `<redacted>` (keys are kept, a bare `?abc123` becomes `?<redacted>`), drops `user:password@`, redacts the value of a `;name=value` path parameter (`;jsessionid=...`), and cuts every URL that is not http(s) or ws(s) to its scheme (`javascript:`, `mailto:`, `tel:`; `data:` keeps its mime type; a link `href` in a locator is cut the same way and clipped to 2 KB). URLs inside console text are found too, including IPv6 hosts, `javascript:` and `mailto:` URLs and relative URLs that carry a query (`/api/me?token=...`). A token in a *path segment* (`/verify/abc123`) is not recognised. `evidence_urls="full"` writes them as they were and is for private use only. `Agent(urls=...)` and the `config` in `run_start` are written as given. Even redacted, the directory is not guaranteed safe to share: **screenshots are images of the page and are not redacted**, and a secret that you did not declare and that appears in page *text* (a title, a console message that is not a URL, a confirmation page) is written as it appears. Review a run directory before attaching it to a public issue.

Limits of the capture: it listens to the agent's own tab only (`Target.setAutoAttach` is not called), so a cross-origin iframe (payment, OAuth), a worker or a popup sends no console or network events, and "0 failed requests" does not cover them. If the tab detaches or crashes while the socket stays open (`Target.detachedFromTarget` for this session, `Inspector.targetCrashed`), that is a `capture_lost` too. It opens a second websocket to the browser and enables `Runtime`, `Log` and `Network` on its own session; that needs a **multi-client CDP endpoint** (a local Chrome is one; a hosted endpoint that allows one client per URL may drop the first client, which is the agent's own connection). `Agent(evidence_capture=False)` skips the second socket: trace, screenshots and locators remain, console and network are marked unavailable. A page can observe `Runtime.enable` (a known anti-bot signal). `BU_CDP_URL` must be `http(s):` and `BU_CDP_WS` `ws(s):`. The HAR has the required HAR 1.2 fields with their types (checked in the tests by a small structural check; no external HAR validator is run), `httpVersion` is `unknown`, and there are no `pages`.

Every executed click, fill, select or hover also records a **locator** in its `action` event, and in `history[i]["locator"]` (`locators=True` turns that on without `evidence_dir`): the element's `role` and accessible `name`, `tag`, `type`, the `href` (path, with query values and fragment `<redacted>` unless `evidence_urls="full"`) and `href_origin` (the scheme and host, with port, of an http(s) link; a relative link carries the page's own origin; `null` for anything else), `label_for`, `placeholder`, `test_id` (the first of `data-testid`, `data-test`, `data-qa`, `data-cy`), `id` only when it is not generated-looking and unique in the document (a delimited all-digit segment such as `mat-input-3`, `radix-0`, `rc_select_0`, long hex or digit runs, `:r1:` and `ember123` are dropped; an id is a hint, never the only key), the `scope` (the nearest named dialog, form, list item, row, article, region, nav, main or banner: its `role` and `name`, its `ordinal` and `count` among scopes with the same role and name in the document, and its own `css_path`; unnamed containers are skipped; a row is named by its heading or first text, not its whole text), the `ordinal` of the element among the **shown** controls with the same role and name inside that scope and in the whole document (with both counts; hidden duplicates are not counted, as the snapshot does not offer them), its trimmed `text` (empty for a `select`, `textarea` or editable element, so a field's current content is not recorded), a `css_path` from the nearest ancestor with a usable id, and its `rect` (viewport pixels at the time of the action: informational). `Browser.resolve(locator)` is the inverse, and its rule is *the same element, or nothing, never another one*. It first reads a **unique test id** (rule `test_id_first`): when the locator's `test_id` was unique in the document when recorded (`test_id_unique`), exactly one element has it now, the recorded scope is absent, had `count` 1, or had a larger `count` that still equals the number of scopes with the recorded role and name (the hit must then lie in the scope at the recorded `ordinal`), that element still has the recorded tag, type, role, accessible name, text and, for a link, target, and (when a scope was recorded) it lies inside the scope element found by the recorded role, name and ordinal, it is the answer, whatever the look-alikes' container shows now. A test id outside that scope (for example a position-derived id such as `delete-1` that now sits in another row) is ignored and the primary rule below decides. A test id is an explicit identity the page author placed, and uniqueness at both times plus name, role and text verification is a stronger identity than role, name and position; without this, a control that shares its role and name with other elements was judged by the digest of their whole container, which holds live data (prices, greetings) and made every replay heal an unchanged page. The primary rule is still evaluated, and a disagreeing primary rule wins as a refusal: if it resolves a different verified element, the result is `ambiguous` with no element; if it refuses (the digest changed, the counts differ) or resolves the same element, the test id stands. The residual: a test id moved onto a same-role, same-name, same-text look-alike is not noticed when the primary rule refuses instead of resolving a different element, either because a look-alike was added (the counts differ) or because the container text changed (the digest differs). A test id that was not unique when recorded or is not unique now never resolves this way, and every other case continues below. A stable `id` gets no such first read: ids are often framework-owned, reused across forms and labels, and the recorded-unique id is weaker evidence than an attribute meant for tests, so it stays a fallback. Before the count and digest rules, a control that was the only one with its role and name in the whole document when recorded (`ordinal.document_count` 1) and is still the only shown one, that `verifies` and, when a scope was recorded, the number of scopes with the recorded scope role and name still equals the recorded `count` and the control lies inside the one at the recorded `ordinal` (a param-bound scope uses this run's value; no scope condition when none was recorded), resolves with rule `unique_in_document`, even when sibling scopes share a name and hold live data. When only one element with this role and name exists anywhere, the scope digest cannot pick a different one; the count and ordinal conditions are the same as the test id rule's, and keep a unique control that moved to a differently named section (the only `Delete`, now under another person), to another record of a same-named list (a per-row action that appears on one row at a time) or into a list that gained or lost a record from resolving; a primary rule that resolves a different verified element still wins as `ambiguous`. Residual: the same ordinal of a same-named list now holds a different record (a re-sort that keeps the count), which is the live-data case the digest was giving up on by design. Scopes hidden when recorded are not counted (tab panels of the same name show `count` 1), so for them the count guards nothing. Otherwise it takes the controls with the recorded role and name inside the recorded scope (the scope itself found by role + name + ordinal; a control without a role, such as a password field, is matched by tag and type instead) and accepts one only if the recorded in-scope (or document) count equals the current one and, when there is a scope, the recorded scope count equals the current scope count. When position alone would decide (several controls match in the scope, or sibling scopes share a name, or there is no scope and several match in the document) it also needs the locator's `digest` to equal the digest of the look-alikes' own container now: the smallest common ancestor of the matching controls (their list, not the page), or the scope when only one control matches. The digest hashes the container's whole text (no clip), whitespace-normalised, hidden text and field values excluded, as 64 bits (two independent 32-bit lanes, cyrb53-style); a container with more than 20000 text nodes has no digest, which counts as unresolvable (`ambiguous`), never as equal. A re-sorted list with the same count and names therefore does not resolve, while the unchanged page still does; the result then carries `digest_changed: true` and a replay reports the cause `digest_changed`. A locator without a digest (schema 1) cannot prove this and is `ambiguous` in those cases. Text outside the look-alikes' container (a clock, a banner, a status line) is not in the digest; volatile text inside it (votes, "2 min ago", a price) is, and makes the step heal, the safe direction. Blind spots, by design: rows that differ only in input values (replay's own fills change them), in image `src` or `alt`, in link targets or in `aria-label`-only content have equal digests (a link's origin, path and query keys are compared separately, see below). A lone survivor is accepted only if the recorded count was also 1; if three equal rows were recorded and one is left, it refuses with `rule: "ambiguous"`, whichever row was the target. Equal counts alone do not prove the same element, which is why look-alikes also need the digest, and the digest does not prove it either where the blind spots above apply; a deleted row replaced by one with the same text still passes, as nothing in role, name, scope or text tells them apart. A stable `id`, which does not come from that rule, is accepted only if (a) the recorded scope is absent or had `count` 1, (b) the id was unique in the document when recorded (`test_id_unique`, `id_unique` in the locator) and is unique now, and (c) the element still has the recorded tag, type, role, accessible name and text and, for a link, the recorded target (origin, path and query keys; query values are redacted in a trace and not compared). A shared test id, such as `delete` on every row, therefore never resolves to another row's control after the target's row is gone: it comes back as a hint or nothing. A renamed scope, or an id that moves into a differently named scope, is not found by the recorded scope, so it is not resolved by a test id either. There are three outcomes. **Resolved**: `rule` is `test_id_first` (it replaces the earlier `test_id`), `role_name_scope` or `id`, `verified` is true, and `tag` and `text` describe the element. **Ambiguous**: several controls matched and the counts no longer hold; no element. **Hint or none**: `css_path` is never a resolution; when it still points at something the result is `rule: "hint"` with `hint: {tag, text}` of whatever is there now, and no element, for the caller to show or ignore; `None` when nothing matches. The result is `{rule, unique, count_match, verified, tag, text, hint}` (`resolve(locator, node=True)` adds `node`, the id the last observation gave the element or `None`; a replay uses it to find the action to run); for a `test_id_first` or `id` result `count_match` is `null` (no count was compared) and `unique` is `true`. `text` is the element's trimmed text, empty for an editable element, a `select` or a `textarea`, as in the locator. A replay must compare names clipped to 80 characters, as `locator` does. An element in a shadow root or a frame has no locator (it could never be found again): `locator_error: "NotInDocument"`. If an executed element action has no locator, the `action` event says why in `locator_error` (`ElementGone`, `NoNode`, `NotInDocument`, or the exception class) and `run_end.totals.locator_missing` counts them, so a replayer can refuse such a trace up front. The function lives in `a11y.js` beside role and name, so a replay can use the same code. Cost: with evidence on, a non-navigating click tick adds one locator read and the trace writes; a screenshot adds its own capture (the lane prints both).

### Record and replay

A test runner wants the property that a run which passed is deterministic and free when the page has not changed. Record with `evidence_dir`, replay with `replay=`:

```python
Agent(url, steps, values=values, evidence_dir="runs/signup-1")           # asks the model for every action
Agent(url, steps, values=values, replay="runs/signup-1/trace.jsonl")      # asks it for nothing, unless a step diverges
```

Pass the same steps (checks are code and are not stored) and the same value names. The goals and check descriptions (whitespace-normalised) and the value names of the trace must equal the ones given, and the trace must end `done` with `verified` true, otherwise the `Agent` raises `ValueError` before any browser is opened (`replay_mismatch`, `replay_requires_verified`): a trace is never replayed for another task. `replay` is a path or the events from `jev_ultrafast.trace.load_trace`.

For each step the agent takes the recorded executed actions in order and, with no model call, observes the page and re-resolves the action: an element action through `Browser.resolve(locator)` (the same element or nothing, see above) mapped to the action of the same kind that the observation offers for that node; a key, back, reload, goto, scroll or wait through its id, so it must still be declared and offered. A fill types the caller's current value for a recorded `value:<name>` (a secret is never in the trace and comes from the caller again), the recorded text for a non-secret generated one, and the recorded option for a select. The action then runs through the normal path: freshness, `before_action`, refusal handling, settle, history and evidence, marked `source: "replay"` (`"model"` otherwise, in `history[i]["source"]` and the `action` event). When the step's checks hold twice (the usual stable double read) the step is done and the rest of its recorded actions are skipped. A `before_action` veto ends the run `denied`, exactly as for a model action; it is never healed around. A replayed action does not take part in the `stuck_after` rule (the recorded run passed it and the plan is finite; a page that stopped reacting is a divergence). Whether an action ran is decided by the history, never by the exception type: if the observation after an executed action goes stale, the action is done and is not run again.

**Divergence** is: the locator resolves to nothing, to a hint or to an ambiguous set; the kind is not offered for that element (or the key, page or scroll is not offered any more); the action was refused or found stale twice in a row; the recorded actions of the step are spent while its checks do not hold; the recorded locator is missing (`run_end.totals.locator_missing`: those actions always heal); a generated text was recorded as a secret marker, was cut, or a value name is missing; a `goto` whose declared page now has another URL (`goto_url_changed`: scheme, host, path and the query **keys** are compared, values are redacted in the trace); a scroll of another distance (`scroll_changed`); a key whose focused element is not the recorded one (`focus_changed`: role, label, tag, type and the redacted `href` are compared, and the recorded focus locator must resolve like a click's to the node that has focus now, so two look-alike links or buttons are told apart) or whose trace did not record it; an action on another page than the one it was recorded on (`page_changed`, from `page_url`, recorded on every action event): a `back`, `reload`, `scroll` or `wait` needs the same scheme, host, path and query keys, and a `click`, `fill`, `select`, `hover` or `key` the same scheme, host and path (the query may vary: a page number), so a recorded "Save" is never clicked on whatever page a heal left to; a schema 2 trace without `page_url` heals, a schema 1 trace has none and its element actions are not bound to a page; a link whose scheme or host is not the recorded one is not the same element (its text and path alone do not make it one); a locator that resolves only through the look-alikes' digest changing (`digest_changed`); a select whose option was not recorded (`option_unavailable`); and checks that held once but not again after the settle (`checks_unstable`, an optimistic page that took the press back: the model loop would reject this, a replay hands it over instead). With `heal=True` (default) the rest of that step goes to the normal model loop (the step's goal, checks and values; budgets apply) and replay resumes at the next step. With `heal=False` the run ends `diverged` and `stop_reason` names the cause and the step (`"ambiguous at step 2"`); nothing is executed after the divergence. A mutation that was executed is never retried. A `heal` event in `trace.jsonl` records the step, the cause and the model calls it spent; `state["replay"]` is `{steps_replayed, steps_healed, actions_replayed, model_calls}` and `run_end.totals` gains `replay_actions` and `healed_steps`. The trace of a healed run is itself a valid trace to replay next time.

**Routes and ids.** The route comparison of a `click`, `fill`, `select`, `hover` or `key` ignores the fragment, so a hash-routed app (`/#/inbox`, `/#/sent`) is one route for every hash (a `back`, `reload`, `scroll` or `wait` compares the redacted URL, whose fragment is only marked as present). A `mailto:` or `tel:` link compares by scheme only: the address or number is redacted before the trace is written, so two such links of the same element differ only if the scheme does. An app whose path carries a new resource id per run (`/chat/<uuid>`) would never match its own recording, so for the page comparison above both sides have every id-like path segment replaced by one marker before they are compared: a UUID, a hex run of 8 or more characters with at least one digit, an all-digit segment, and a token of 16 or more base64url characters with both letters and digits. `/chat/<uuid-a>` and `/chat/<uuid-b>` are the same page, `/a/123` and `/a/124` too, while `/chat/new` and `/chat/<uuid>`, or `/a/settings` and `/a/admin`, are not. A path the heuristic cannot tell apart (a slug such as `/orders/pending`) is declared with `replay_routes=[r"^/orders/[^/]+$"]`: a list of regular expressions (strings or compiled), and any path one of them matches **in full** (`re.fullmatch`, the whole path, so `r"/orders/"` alone matches nothing) is compared by pattern, not by text, whatever its value. A declared `goto` URL is still compared exactly (scheme, host, path and query keys). The heuristic is deliberately plain: a long hyphenated slug that contains a digit looks like a token, and wizard steps (`/checkout/step/1` and `/checkout/step/2`) and years (`/reports/2024/export` and `/reports/2025/export`) are all-digit segments, so they compare equal too (a skipped step can reach a same-shaped `Next` button); declare `replay_routes` or an `expect` check for those. **Destructive flows:** because of this rule `/users/<id>/delete` on another id is the same page, and a button has no id in its locator, so the replay can press `Delete user` for another user; give such a step an `expect` check that names the resource, or a `before_action` veto, or turn the rule off with `replay_id_segments=False` (paths are then compared exactly; a declared `replay_routes` pattern still applies). Links are different: the href of a link keeps its id, so an id-bearing link (`/chat/<uuid>/rename`) does not replay across ids; the step heals (or diverges) instead.

A trace is trusted input: a hand-edited `value_name` can aim a declared secret at another field (the `before_action` hook still sees the name), and the start URL, `urls` and `keys` of the new run are not compared with the trace on purpose, because environments change. The value names and their secret flags must equal the recorded ones (`replay_mismatch: value secrecy differs`).

On a replay the quiet window that `stable()` waits before the second check read is `replay_quiet_ms` (default 150; `None` always keeps the full 500 ms) instead of 500 ms, only when the post-action settle is on, no request is in flight or started and no short timer was armed since the action, the page-side tracker answered (an unknown activity keeps the full window), and every check of the step is cheap; the second read always happens, and a model run keeps its full window. The short window trusts the tracker's counters: it catches an optimistic rollback that needs a counted `fetch` or `XMLHttpRequest` or a short `setTimeout`, and cannot see one driven by a WebSocket, server-sent events or `postMessage`, a `setInterval`, an endpoint listed in `ignore_urls`, or a timer armed after a new document loaded. Only the full window (`replay_quiet_ms=None`) catches those, when they land within 500 ms of the last DOM change; a browser fixture with a `setInterval` rollback pins that. Measured in CI (headless Chrome, 3 steps, 4 actions, a stubbed model with no latency, median of 5): recorded 1740 ms, replayed 701 ms, and 0 model calls against 4 or more; with a real model the recorded run also pays each call's latency. The browser lane prints both numbers in its job summary.

What does not heal by itself, or is out of reach: a page that changes what a `generated` text should be (the recorded text is typed as it was; record with `values=` for anything that varies); content in iframes or shadow roots (no locator, so the action heals every time); the resolve limits above (a row replaced by one with the same text is replayed); a check callable that depends on state the replay does not reproduce; and server-side effects, which the checks are there to verify. A trace is not secret-free by design if the page showed the secret in a way the scrub does not cover (see Values); keep traces as private as screenshots.

## Why it moves

- **One request per decision cycle.** Operation and target heads share the same observed state.
- **No screenshots in the default agent loop.** Jev consumes structured state. The inspector opts into screenshots; the video uses a separate continuous screencast.
- **One browser call per snapshot.** Read visible controls, their names, values, and text atomically. Keep references to the actual DOM nodes.
- **Validate the selected target.** Clicks check the document, form values, target, and nearby context. Animation alone does not force another prediction. Resolve current geometry and reject covered controls before input.
- **Wait for useful state.** After typing into a combobox, wait for visible suggestions, capped at 200 ms. Other interactions get at most two animation frames or 50 ms. These reads happen after execution is logged.
- **Keep the owned tab rendering.** The agent drives a tab opened in the background, with focus emulation. In headless Chrome a background tab inside the existing window is throttled to about one frame per second after its first clicks, and every pointer move then waits about 1 s for the next frame (measured in CI: a click step went from 1033 ms to 50 ms median). So `new_window=None` (the default) opens the tab in a window of its own when its user agent says `HeadlessChrome` (its product string says plain `Chrome`), and in a tab of the current window otherwise; `True` and `False` force either. Headed Chrome was not measured (a new window there is a visible one, and CDP does not say whether it takes focus), and no CI job covers it.
- **Send visible text.** Offscreen article bodies and footers do not fill the model context.
- **Reuse an interrupted text request.** A generated value survives a stale-page retry only if the entire text-helper input is unchanged.

Every executed target is resolved from an observed node. The executor rechecks page freshness and click occlusion. Model output never becomes selectors, coordinates, shell commands, or executable JavaScript. Text-helper output must parse as a small JSON object before typing.

## Evidence and limits

The current video is a **7,073 ms** Google Flights run. Timing starts after initial page observation and includes model calls, generated text, browser work, stale decisions, and loading waits. A fresh independent check verifies the one-way setting, Zürich, London, September 20, 2026, and visible flight options. The video plays at 1×, with no opening hold and a 0.5-second final hold.

In six alternating runs with identical models and settings, both versions passed **3/3**. Median task time went from **9.450 s → 7.092 s**, a **25% reduction**; median browser protocol calls went from **1,092 → 101**. This is three repeats of one task on one browser profile, not a general reliability benchmark.

The same policy opened the requested Wikipedia article in **2.798 s** and passed a local hotel search/filter task in **1.896 s**. Runs, failures, source hashes, and measurement boundaries are in [performance.md](docs/performance.md).

A `DONE` choice still requires independent outcome verification. The DOM reader handles common HTML and ARIA controls, not the full accessible-name specification. Controls hidden by `display`, `visibility`, `aria-hidden`, or `inert` stay unlisted until something else (for example `HOVER` on a parent) shows them. A hover menu whose parent carries none of the hover signals above (for example a bare `<div>` with a CSS `:hover` rule) is not offered `HOVER`, so give such a parent `aria-haspopup`. Shadow roots, frames, canvas, uploads, pop-up tabs, and nested scrolling remain outside this MVP; keyboard support is the fixed key set and the shortcuts you declare. Owned tabs share the existing Chrome profile.
